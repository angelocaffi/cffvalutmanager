## Fase 1 — MVP

- [x] Fondamenta `Web.Client` + pagina di login/sblocco ([features/encryption-key-management.md](features/encryption-key-management.md)) — primo pezzo di UI Blazor mai costruito, verificato live in browser (non solo compilato), prerequisito per tutte le pagine ancora segnate "manca" più sotto. Nuovo `POST /api/auth/prelogin`: un client su un device nuovo non aveva modo di scoprire il proprio salt/parametri KDF prima di poter calcolare l'auth hash per il login — gap scoperto solo costruendo la UI reale. Anti-enumeration sullo stesso modello del login (salt fittizio ma stabile per email sconosciuta, derivato da un pepper di processo). `SessionState` (token + DEK sbloccata, tutto solo in memoria — un refresh di pagina vero richiede sempre un nuovo login, mai persistito in localStorage/sessionStorage) + `VaultAuthenticationStateProvider` collegano lo stato al meccanismo standard `[Authorize]`/`AuthorizeRouteView` di Blazor, così le pagine future si proteggono con un semplice `@attribute [Authorize]`. CORS aggiunto sull'Api (host separato dal client in dev). **Due bug scoperti solo verificando dal vivo in un browser reale** (mai nei test, che girano sul runtime .NET normale): (1) `Konscious.Security.Cryptography.Argon2.GetBytes()` sincrono blocca su un `Task.Result` interno, che Blazor WASM single-thread rifiuta con `PlatformNotSupportedException` — risolto con `IKeyDerivationService.DeriveKekAsync`, vedi [features/encryption-key-management.md](features/encryption-key-management.md); (2) le migration non erano mai state applicate contro un vero SQL Server (solo contro SQLite in-memory nei test) e fallivano per conflitto di cascade path (`Vault → Folder`/`Vault → Tag` cambiati da `Cascade` a `Restrict`), vedi [data-model.md](data-model.md). 9 nuovi test (7 Crypto per `DeriveKekAsync` + 2 Api per `/prelogin`; 326 in totale nella solution). Refresh automatico del token in background ora implementato: `TokenRefreshScheduler` legge il claim `exp` dell'access token (`JwtParser.GetExpiryUtc`) e richiama `POST /api/auth/refresh` circa un minuto prima della scadenza, senza mai toccare la DEK; un refresh rifiutato (token revocato) chiude la sessione come un qualunque fallimento di autenticazione, un errore di rete transitorio viene ritentato a breve. Verificato dal vivo abbassando temporaneamente a 20s la durata dell'access token lato server: la sessione sopravvive oltre quella finestra con refresh silenziosi ripetuti, poi la modifica temporanea è stata annullata prima del commit. Registrazione/provisioning tenant via UI ora implementata (`/register`): stesso pattern crittografico di `Login.razor` ma generando materiale nuovo invece di sbloccare quello esistente (salt, KEK via Argon2id con i parametri di produzione, DEK generato e wrappato, tutto client-side — il server riceve solo byte opachi). Verificato dal vivo: registrazione, login immediato con le credenziali appena create (round-trip reale Argon2id/AES-256-GCM), e conflitto pulito su slug/email duplicati.

## Fase 2 — Hardening e qualità

- [x] Rate limiting e lockout su login ([features/authentication.md](features/authentication.md)) — due livelli: lockout per account (`User.FailedLoginAttempts`/`LockedUntil`, 5 tentativi falliti consecutivi → 15 minuti di blocco a finestra fissa, condiviso tra password e codice MFA errati) e rate limiting per IP (`Microsoft.AspNetCore.RateLimiting`, 10 richieste/minuto su login/mfa-verify/refresh, nessuna coda). 8 nuovi test (6 Infrastructure + 2 Api; 281 in totale nella solution)
- [x] Logout remoto / gestione sessioni attive ([features/authentication.md](features/authentication.md)) — `GET /api/auth/sessions` (elenco sessioni attive, una per `RefreshToken` non revocato/non scaduto), `POST .../sessions/{id}/revoke`, `POST .../sessions/revoke-all` (`AuditAction.SessionsRevoked`). Limite accettato: un access token JWT già emesso resta valido fino alla sua scadenza naturale (15 min) — nessuna blocklist server-side per revoca puntuale di JWT stateless, stessa scelta già fatta per la sospensione tenant. 12 nuovi test (7 Infrastructure + 5 Api; 293 in totale nella solution)
- [x] Cambio master password ([features/authentication.md](features/authentication.md)) — `POST /api/auth/change-master-password` (autenticato), `IChangeMasterPasswordService`/`ChangeMasterPasswordService`. Ri-cifra solo la DEK, mai i singoli vault item: il client deriva la nuova KEK dalla nuova master password, ri-wrappa la DEK già sbloccata con la vecchia e manda al server solo `NewEncryptedDek`/`NewMasterPasswordSalt`/nuovi parametri KDF, oltre a `CurrentAuthHash` per provare di conoscere la password attuale (il server non vede mai una master password, vecchia o nuova, in chiaro). Al successo revoca **tutte** le sessioni attive (incluso il chiamante corrente, tramite `IRefreshTokenService.RevokeAllSessionsAsync`) — ogni dispositivo deve ri-autenticarsi con la nuova master password. Azione tracciata con il nuovo `AuditAction.MasterPasswordChanged`. 3 nuovi test Infrastructure (in `AuthenticationTests`)
- [x] Rotazione DEK indipendente dal cambio master password ([features/encryption-key-management.md](features/encryption-key-management.md)) — `POST /api/auth/rotate-dek` (autenticato), `IDekRotationService`/`DekRotationService`. A differenza del cambio master password (ri-wrappa la stessa DEK sotto una KEK nuova), qui il client genera una DEK **nuova**, ri-cifra ogni voce corrente del proprio vault personale e manda `NewEncryptedDek` + l'insieme delle voci ri-cifrate; il server valida che copra esattamente le voci attuali non cancellate (stesso pattern di `VaultMembershipService.RevokeAsync`), in una transazione atomica. Scope solo vault personale: le voci di un vault di organizzazione (DEK del vault) e le voci già condivise (chiave dedicata per-voce, `ItemMembership`) non rientrano. Nessuna revoca sessioni (la KEK non cambia). Verificato dal vivo contro il database reale: insieme non corrispondente → 409, insieme corretto → 204 con payload e `EncryptedDek` confermati aggiornati. 10 nuovi test (7 Infrastructure + 3 Api; 459 in totale nella solution). Nessuna UI Blazor ancora costruita (lavoro solo lato API su richiesta esplicita)
- [x] Verifica email in registrazione ([features/authentication.md](features/authentication.md)) — riusa l'entità `OneTimeCode` scaffoldata da Fase 0 (mai usata finora). Un codice numerico a 6 cifre viene generato e inviato automaticamente alla fine di `ProvisionTenantService.ProvisionAsync`/`UserRegistrationService.RegisterInTenantAsync` (nuova dipendenza opzionale `IEmailVerificationService?` su entrambi, sul modello del default opzionale già usato da `ServerAuthHashHasher` — nessun test esistente rompe). `POST /api/auth/email-verification/resend` (cooldown 60s, no-op se già verificata) e `POST /api/auth/email-verification/confirm` (scadenza 10 min, max 5 tentativi per codice) sono entrambi pubblici e anti-enumeration (risposta identica per email inesistente/codice sbagliato/già verificata), rate-limitati come gli altri endpoint auth pubblici. Il codice è hashato a riposo con HMAC-SHA256 salato per record — non Argon2id: è un valore a bassa entropia e vita breve, le difese reali contro il brute force sono la scadenza, il limite tentativi e il rate limiting IP, non un hash costoso. Riusa gli `AuditAction` esistenti `EmailOtpRequested`/`EmailOtpVerified`/`EmailOtpFailed` (già scaffoldati da Fase 0 in previsione anche del futuro fattore MFA Email OTP, Fase 3). Nuova colonna `User.EmailVerifiedAt` (migration `AddUserEmailVerification`, su/giù verificati). Nessun provider email reale ancora collegato: `IEmailSender`/`LoggingEmailSender` sono un placeholder che logga senza consegnare — va sostituito prima di un rilascio in produzione. 12 nuovi test (7 Infrastructure + 5 Api; 305→317 in totale nella solution)
- [x] Review di sicurezza completa contro la checklist in [security-model.md](security-model.md) — prima revisione adversariale dell'intera codebase (dettagli e cronologia in [security-model.md#stato-revisione-sicurezza](security-model.md#stato-revisione-sicurezza)). Risolti: auto-invito/revoca su vault organizzativi da parte di un Admin non membro (F-HIGH-1), timing side-channel di enumerazione email nel login (F-MED-1), provisioning tenant senza rate limiting e con 500 non gestito su duplicato (F-LOW-1), audit log mancante su restore/eliminazione fisica/tag e su tutte le mutazioni di cartelle e tag (F-LOW-2, nuovo `AuditAction.PermanentlyDeleted`), mancanza di HSTS e di `ForwardedHeaders` dietro reverse proxy (F-LOW-3), revoca passiva (mai attuata) della catena di refresh token al rilevamento di un riuso (F-INFO-1). Tutti coperti da test di regressione. 298 test nella solution
- [x] Test di integrazione end-to-end su flussi critici (login, cifratura/decifratura, cambio master password) — **login**: già coperto end-to-end su HTTP reale in `AuthAndRolesTests` (provisioning→login, refresh con rotazione, setup/verifica MFA, ruoli). **Cifratura/decifratura**: `CryptoRoundTripTests` — a differenza degli altri test vault-core (che usano byte casuali opachi, corretto perché il server non deve mai vedere il contenuto), questo usa i servizi reali di `CffVaultManager.Crypto` per derivare la KEK da una master password (Argon2id), generare e wrappare una DEK, effettuare il provisioning/login via HTTP reale, ri-derivare la KEK dai materiali restituiti dal login (simulando una sessione/dispositivo nuovo), sbloccare la DEK e verificare che sia bit-per-bit identica all'originale, poi cifrare/decifrare un vero payload di un vault item attraverso l'endpoint reale — provando che l'intera pipeline crittografica client-side interopera davvero col percorso di storage/recupero del server, non solo che ogni pezzo funziona isolatamente. Include anche un test che verifica che un DEK sbagliato fallisca l'autenticazione AEAD invece di restituire testo in chiaro corrotto silenziosamente. **Cambio master password**: implementato (vedi voce dedicata sopra) e coperto negli stessi `CryptoRoundTripTests` — dopo il cambio, la KEK ri-derivata con la nuova master password sblocca una DEK identica bit-per-bit a quella originale, e un vault item creato prima della rotazione resta decifrabile senza essere mai stato toccato. 2 nuovi test Api. In totale, tra questa voce e "Cambio master password" sopra: 5 nuovi test (300→305 in totale nella solution)

- [~] Notifiche (alert sicurezza) ([features/notifications.md](features/notifications.md)) — alert di sicurezza via email implementati (nuovo login da IP sconosciuto, cambio master password, disattivazione fattore MFA/rimozione passkey), riusando `IEmailSender` esistente; scoped deliberatamente a eventi osservabili server-side. 6 nuovi test (385 in totale nella solution), verificato anche dal vivo contro l'Api reale. Notifica di scadenza carta **scartata definitivamente** (non backlog): richiederebbe un campo non cifrato lato server con la data di scadenza, in contrasto col principio di zero-knowledge — vedi [security-model.md](security-model.md#gestione-carte-di-credito--considerazioni-aggiuntive)
- [x] WebAuthn/Passkey come alternativa a TOTP (autenticazione biometrica — Windows Hello/Touch ID/Face ID/sblocco Android — vedi [features/authentication.md](features/authentication.md)) — lato server: `IWebAuthnService`/`WebAuthnService`, crittografia delegata a Fido2NetLib (stesso principio di Konscious per Argon2id e Otp.NET per TOTP). Nuove entità `WebAuthnCredential` (una per dispositivo, nessun flag on/off singolo: la disponibilità del fattore è "ne esiste almeno una") e `WebAuthnCeremony` (stato effimero tra begin/complete, come `OneTimeCode`). Testato lato server con un authenticator virtuale (ECDSA P-256, attestazione "none") che genera risposte realmente firmate, non un mock — ha scoperto due bug reali: ordinamento `DateTimeOffset` non supportato da SQLite in `ListCredentialsAsync`, e un'eccezione diversa da quella attesa lanciata da Fido2NetLib su una firma corrotta (ora gestita, altrimenti un 500 non gestito su input malformato). Lato `Web.Client`: nuovo modulo JS (`wwwroot/js/webauthn.js`) per `navigator.credentials.create()/get()` (conversione base64url↔ArrayBuffer dei soli campi byte, il resto del JSON già combacia con lo standard); `Login.razor` offre il fattore nel selettore MFA con avvio automatico se è l'unico; nuova sezione in `/security` per registrare/elencare/rimuovere dispositivi.
